Effects let you step outside of React and synchronise your components with non-React widget, network or DOM. If no external system involved, you shouldn't need an Effect.

* You don't need Effect to transform your data, eg. filter a list. You can do it at top level of your component, and they will rerun whenever your props or state change.

* You don't need Effect to handle user events. Eg. buy an item, because they can be encapsulated to event handlers.

*  While you can fetch data with Effects, there are better solutions.

---
#### Avoid resetting all state when a prop changes

Below is inefficient because `ProfilePage` and its children will first render with stale value, then render again.

Instead we can assign a `key` prop to each profile. When the key becomes different, the component will unmount (React will see it as a different component), thus clearing out all the state.
```ts
// Bad
const ProfilePage = ({ userId }) => {
	const [comment, setComment] = useState('');

	// Avoid this
	useEffect(() => {
		setComment('');
	}, [userId]);
}

// Good 
const ProfilePage = ({ userId }) => {
	return (
		<Profile userId={userId} key={userId} />
	)
}

```

#### Adjusting some state when a prop change

Sometimes, you want to adjust some state when a prop change.

Eg. We want to reset selection to null when items is a different array.

Every time `items` change, component and its children will render with a stale `selection` at first. then Effect runs and updates the state, which triggers another render.

```ts
// Bad
const List = ({ items }) => {
	const [isReverse, setIsReverse] = useState(false);
	const [selection, setSelection] = useState(null);

	// Avoid
	useEffect(() => {
		setSelection(null);
	}, [items]);
}


// Good
// This allows React to render immediatlet after exit with return statement, before List children has been rendered or DOM updated.
const List = ({ items }) => {
	const [isReverse, setIsReverse] = useState(false);
	const [selection, setSelection] = useState(null);

	// Better to adjust the state while rendering,
	// we can store previous items
	const [previousItems, setPreviousItems] = useState(items);

	if (items !== previousItems) {
		setPreviousItems(items);
		setSeletion(null);
	}
}

// Even better, we just store the selectedId
const List = ({ items }) => {
	const [isReverse, setIsReverse] = useState(false);
	const [selectedId, setSelectedId] = useState(null);

	// Instead just stores the id
	const selection = items.find(item => item.id === selectedId) ?? null;
}
```

Adjusting state based on props or other states makes dataflow difficult to understand. Always see if you can reset state with `key` prop or calculate during rendering.

#### Sharing logic between event handlers

This Effect is unnecessary and may cause bugs.
Eg. If the app remembers shopping cart between page reloads. If you add a product to the cart once and refresh the page, `product.isInCart` will already be true, and will show the notification.

When you are not sure if some code should be in an Effect or event handler, ask why this code is needed. Use Effects only for code that should run because component was displayed to the user.

In this case, notification should appear because user pressed the button, not because page was displayed!
```ts
// Bad
const ProductPage = ({product, addToCart}) => {
	// you want to show a notification when  user puts product in the cart
	useEffect(() => {
		if (product.isInCart) {
			showNotification(`Added ${product.name} to cart`);
		}
	}, [products]);

	const handleBuyClick = () => {
		addToCart(product);
	}

	const handleCheckoutClick = () => {
		addToCart(product);
		navigateTo('/checkout');
	}
}

// Good
const ProductPage = ({product, addToCart}) => {
	// you want to show a notification when  user puts product in the cart
	const buyProduct = () => {
		addToCart(product);
		showNotification('...');
	}

	const handleBuyClick = () => {
		buyProduct();
	}

	const handleCheckoutClick = () => {
		buyProduct();
		navigateTo('/checkout');
	}
}
```

#### Sending a POST request

This form sends two types of POST requests. Sends an analytics event when mounted, and send a post request to `register` endpoint when Submit button clicked.

```ts
const Form = () => {
	const [firstName, setFirstName] = useState('');
	const [lastName, setLastName] = useState('');

	// Good, as it deals with code when component is shown
	useEffect(() => {
		post('/analytics', {eventName: 'visit' });
	})

	// Bad, just remove effect and place post() inside handleSubmit()
	// As it's invoked by user interaction
	const [jsonToSubmit, setJsonToSubmit] = useState(null);

	useEffect(() => {
		if (jsonToSubmit !== null) {
			post('/api/register', jsonToSubmit);
		}
	}, [jsonToSubmit]);

	function handleSubmit(e) {
		e.preventDefault();
		setJsonToSubmit({firstName, lastName});
	}
}
```

#### Chaining Effects

Sometimes you feel tempted to chain Effects to update state based on other states.

This is super inefficient, a lot of un-necessary re-renders because we update states incrementally.

Also very hard to extend in case of new requirements.

```ts
// Bad
const Game = () => {
	const [card, setCard] = useState(null);
	const [goldCardCount, setGoldCardCount] = useState(0);
	const [round, setRound] = useState(1);
	const [isGameOver, setIsGameOver] = useState(false);

	// Avoid - chains of effects will trigger each other, inefficient
	useEffect(() => {
		if (card !== null && card.gold) {
			setGoldCardCount(c => c + 1);
		}
	}, [card]);

	useEffect(() => {
		if (goldCardCount > 3) {
			setRound(r => r + 1);
			setGoldCardCount(0);
		}
	}, [goldCardCount]);


	useEffect(() => {
		if (round > 5) {
			setIsGameOVer(true);
		}
	}, [round]);

	useEffect(() => {
		alert('GG');
	}, [isGameOver]);

	function handlePlaceCard(nextCard) {
		if (isGameOver) {
			throw new Error('Game Over');
		} else {
			setcard(nextCard);
		}
	}
}


// Good
// note state is a snapshot within a render, even after calling update. So compute the next state value manually, eg. next round.
const Game = () => {
	const [card, setCard] = useState(null);
	const [goldCardCount, setGoldCardCount] = useState(0);
	const [round, setRound] = useState(1);
	const [isGameOver, setIsGameOver] = useState(false);

	function handlePlaceCard(nextCard) {
		if (nextCard.gold) {
			if (goldCardCount <= 3) {
				setGoldCardCount(g => g + 1);
			} else {
				setGoldCardCount(0);
				setRound(round + 1);
				if (round === 5) alert('Game Over')
			}
		}
	}
}
```

In some cases, you can't calculate next state directly in event handler. Eg. A form with multiple dropdowns where option of next dropdown depends on previous dropdown. Then a chain is appropriate because you are synchronising with network.

Eg. select a country (network call), select a state, select a city.

If no network call, then you can just do it inside event handler and no useEffect will be needed.

#### Initialising the application

Some logic should only run once when app loads.

However note React mount components twice in dev mode. This can causes issues - especially if your logic deals with authentication.

In general your components should be resilient to being remounted.

We can run this sort of code during module initialisation, before the app renders.

Code at top level runs when your component is imported, even if it doesn't end up being rendered. To avoid slow downs, don't overuse this pattern. This applies to not just `App` component, it applies to any component file.


```js
// Note module initialisation applies to every component file

// This code runs once per app load, the first time the component is imported, if the component is not imported anywhere, its top level code won't run.
if (typeof window !== 'undefined') { 
	// Check if we're running in the browser.   
	// ✅ Only runs once per app load 
	CheckAuthToken();
	loadDataFromLocalStorage();
}

function App() {  // ...}
```


#### Notifying parent components about state changes
We want to notify parent component whenever toggle changes.

Recall React batch updates from different components together.
Eg. If I call `setIsOn()` and then `onChange` , React will batch updates into one, so only 1 render.
```ts
// Bad example
// 'Toggle' component updates its state, and React renders.
// Then React runs the effect, with calls OnChange from parent, now parent component will update its state, which starts another React render.

// should remove useEffect and put onChange inside the two click handlers 
// can also move isOn to parent state, and pass it down from parent
function Toggle ({ onChange }) {
	const [isOn, setIsOn] = useState(false);

	useEffect(() => {
		onChange(isOn);
	}, [isOn, onChange]);

	function handleClick() {
		setIsOn(!isOn);
	}

	function handleDragEnd(e) {
		// do stuff...
		setIsOn(!isOn);
	}
}
```


#### Passing data to parent

Here Parent passes setData to child, and relies on Child to call it in useEffect when data changes. This is bad. In React, data flows one way, from parent to child. We should let parent retrieve the data, as both parent and child need it.
```jsx
// Bad
function Parent() {
	const [data, setData] = useState(null);

	return <Child onFetched={setData}></Child>
}

function Child() {
	const data = useSomeAPI();

	useEffect(() => {
		if (data) {
			onFetched(data);
		}
	}, [onFetched, data])
}

// Good
function Parent() {
	const data = useSomeAPI();

	return <Child data={data} />
}
```

#### Subscribing to external store with useSyncExternalStore
Sometimes your component may need to subscribe data outside of React. Eg. from a third party library or built-in browser API.

We need to manually subscribe, as these data changes won't be automatically known by React. Can use a hook.

```jsx
// Bad
function useOnlineStatus() {
	// manual subscription - not ideal
	const [isOnline, setIsOnline] = useState(true);

	useEffect(() => {
		function updateState() {
			setIsOnline(navigator.online);
		}

		updateState();

		window.addEventListener('online', updateState);
		window.addEventListener('offline', updateState);

		// cleanup
		return () => {
			window.removeEventListener('online', updateState);
			window.removeEventListener('offline', updateState);		
		}
	}, []);

	return isOnline;
}

// Using it
function ChatIndicator() {
	const online = useOnlineStatus();
	// do stuff...
}


// Good
// React has a built-in hook for subscribing to external store
function subscribe(callback) {
	window.addEventListener('online', callback);
	window.addEventListener('offline', callback);

	return () => {
		window.addEventListener('online', callback);
		window.addEventListener('offline', callback);
	}
}

function useOnlineStatus() {
	return useSyncExternalStore(
		subscribe, // React won't re-subscribe as long as you pass same function
		() => navigator.online, // get value on the client
		() => true // get value on the server
	);
}
```


#### Fetching data
Here we want to keep results synchronised with data from network given current page and query, hence an Effect.

However, it will kick off separate fetches, in case query changes rapidly. And there's no guarantee which order response will arrive in.

Eg. fetch result for query `hell` comes in after query 'hello', so calls `setResult()` last, which will show the wrong results. This is a race condition.

To clean up, we need cleanup function to ignore stale responses. All requests except for the last one will be ignored.
```js
// No cleanup function
function SearchResults({ query }) {
	const [results, setResults] = useState([]);
	const [page, setPage] = useState(1);

	useEffect(() => {
		fetchResults(query, page).then(json => {
			setResults(json);
		})
	}, [query, page]);

	function handleNextPageClick() {
		setPage(page + 1);
	}
}


// With cleanup function
function SearchResults({ query }) {
	const [results, setResults] = useState([]);
	const [page, setPage] = useState(1);

	useEffect(() => {
		let ignore = false;

		fetchResults(query, page).then(json => {
			if (!ignore) {
				setResults(json);
			}
		});

		// cleanup
		return () => {
			ignore = true;
		}
	}, [query, page]);

	function handleNextClick() {
		setPage(page + 1);
	}
}
```


#### A custom hook for caching data
Imagine user clicks back and we want them to see the previous page instantly without fetching again. Usually this is handled by a framework/library, but for practice sake we can implement this in a hook.

```js
const useData = (url) => {
	const [data, setData] = useState(null);

	// after initial run, useEffect only runs if url changes
	useEffect(() => {
		let ignore = false;

		fetch(url)
			.then(resp => resp.json())
			.then(json => {
				if (!ignore) {
					setData(json);
				}
			});

		return () => {
			ignore = true;
		}
	}, [url]);

	return data;
}


// using it inside some component
// when state updates in the hook, the component will also re-render because it's tracked by React.
const results = useData('/api/search?{query}');
```

* You don't need an Effect if you can calculate during render
* Can use `useMemo` to cache expensive calculations
* We can use `key` prop to unmount component to reset the state of a component tree
* To reset state in response to a prop change, set it during rendering
* Code that runs because component was displayed should be in Effects, others should be in event handlers.
* If you need to update state of several components, better to do in a single event.
* When you try to synchronise states in different components, consider lift up state.
* For fetching data with Effects, implement cleanup to avoid race conditions.
